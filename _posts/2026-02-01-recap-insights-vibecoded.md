Over the Christmas holidays last year, I built a small personal side project end-to-end using my personal GitHub Copilot subscription. A lot of folks call this "vibe coding." I mostly let Copilot do the typing while I kept the direction steady.

The project is now open source: [recap-insights](https://github.com/svaza/recap-insights) is a React + TypeScript app that turns your Strava and intervals.icu data into shareable recaps.

<!--more-->

## What it does

Recap Insights connects to Strava and intervals.icu, pulls activity data through a backend API, and turns it into:

- **Activity analytics** (volume, stats, trends)
- **Flexible time windows** (rolling days, monthly, yearly)
- **Visual recaps** (posters and flyers you can download)
- **"Wow" moments** (biggest efforts and highlights)

It is fully responsive, so it works on desktop and mobile without special casing.

---

## The architecture (intentionally boring)

I kept the architecture tight and predictable:

- **Frontend:** React 19 + TypeScript + Vite
- **Hosting:** Azure Static Web Apps
- **API:** Azure Functions backend (`strava-recap-api`)
- **Routing:** SPA with `staticwebapp.config.json` fallback

That separation let the AI assistants focus on UI and component work while the API stayed cleanly isolated.

---

## The guardrails that made vibe coding work

Vibe coding only works if the boundaries are clear. My constraints were simple:

- Clear vision: a focused POC to generate recap insights for my Strava activities
- Small scope: two pages, minimal moving parts
- Guardrails: I steered the UI flow, backend patterns, and overall structure
- Deployment target decided up front: Azure Static Web Apps + Cloudflare custom domain

Result: I finished it in 3 days, with about 5-6 hours of build time. Roughly 99% of the code was generated by Copilot. My contribution was keeping the project sane: choosing structure, connecting the pieces, fixing edge cases, and doing a final pass for readability and maintainability.

---

## Custom instructions matter more than prompts

The most important trick was **custom instructions**. I treated them like a compact spec: scope boundaries, architecture intent, UX rules, and security constraints. Those instructions keep Copilot and LLMs from drifting when the session gets long or the changes get messy.

They also make the output more consistent across tools. When your instructions are clear, you can move between Copilot, Claude Sonnet, and Opus without resetting the context every time.

I am also experimenting with **GitHub Speckit**, which tries to add a process to this flow by making planning, checkpoints, and structure first-class. It is an early attempt to keep human intent aligned with AI output instead of letting the tool run away with the implementation.

## How I used models

- **Copilot:** raw coding and glue work
- **Claude Sonnet 4.5:** day-to-day iteration and UI scaffolding
- **Claude Opus 4.5:** heavier refactors and complex reasoning
- **ChatGPT Thinking:** research on Strava and intervals.icu integration details

---

## Takeaways

- Be the architect, not the typist. AI is great at output; you still own the direction.
- Start with constraints (scope, deployment, data boundaries). That is what prevents drift.
- Treat generated code like a PR you did not write. Review it, refactor it, and do not merge and pray.
- Use models intentionally: a fast model for most prompts, a stronger one for heavy refactors.
- Be strict about security: never paste tokens, and do not accept auth patterns you cannot explain.
